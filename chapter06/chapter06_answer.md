# 2. 정규화 전 큰 테이블의 문제 찾기

본문의 `library_records_raw` 구조를 기준으로 생각합니다.

```text
library_records_raw 한 행
→ 대여 사건 한 건이지만 회원·도서의 현재 사실까지 함께 저장된 구조
```

## 2-1. 위험한 중복과 의미 있는 반복 구분

| 반복되는 값/상황 | 위험한 중복 / 의미 있는 반복 | 판단 이유 |
| --- | --- | --- |
| 회원 이메일이 여러 대여 행에 반복 | 위험한 중복 | 이메일 변경 시 해당 회원의 모든 대여 행을 수정해야 함 |
| 도서 제목이 여러 대여 행에 반복 | 위험한 중복 | 제목 변경 시 관련 대여 행을 모두 수정해야 함 |
| `loans_nf.member_id = 101` 반복 | 의미 있는 반복 | 한 회원이 여러 번 대여할 수 있어 회원 ID 반복은 자연스러움 |
| 사건 당시 가격 같은 이력값 반복 | 의미 있는 반복 | 사건 당시의 값을 기록해 두어야 과거 상태를 보존할 수 있음 |

## 2-2. 이상 현상 설명

### 삽입 이상

```text
아직 한 번도 대여되지 않은 새 도서를 등록하려 할 때 생기는 문제: 대여되지 않은 새 도서를 등록하려면 대여 정보도 함께 입력해야 하는 문제가 생김
```

### 수정 이상

```text
회원 이메일이 변경될 때 생기는 문제: 회원 이메일 변경 시 해당 회원의 모든 대여 행을 수정해야 함
```

### 삭제 이상

```text
마지막 대여 기록을 삭제할 때 생길 수 있는 문제: 회원의 마지막 대여 기록을 삭제하면 대여 정보와 함께 저장된 회원 정보까지 사라질 수 있음
```

### 왜 이것이 SQL 문법 문제가 아니라 구조 문제인가요?

```text
회원과 도서, 그리고 대여 정보가 하나의 테이블에서 관리되고 있기에 생기는 문제로 이는 SQL 문법상으로는 문제 없이 조회할 수 있으나 DML문 작성 시 업무 상 오류가 ㅂ라생할 수 있음
```

# 3. 1NF·2NF·3NF 핵심 질문 복습

정규형 이름만 외우지 말고 **왜 분리하는지** 설명합니다.

## 3-1. 제1정규형(1NF)

```text
한 셀에 쉼표로 여러 독립 값을 넣거나 book1/book2/book3처럼 반복 열을 만들면 왜 문제가 되는가: 값을 하나씩 조회하거나 수정, 삭제하기 어렵고 같은 정보를 여러 방식으로 저장해 오류가 생길 수 있음
```

내 서비스에서 비슷한 위험이 있는 예:

```text
한 투자 기록의 매수 근거를 ‘실적 개선, 저평가, 수급 유입’처럼 한 칸에 묶어 저장하는 경우
근거별로 검색하거나 수정하기 어려우므로 근거를 각각 나누어 저장해야 함
```

## 3-2. 제2정규형(2NF)

다음 관계를 설명합니다.

```text
(student_id, course_id) → grade: 앞의 두 개가 복합키이고 grade는 두 키의 조합에 따라 결정됨
student_id → student_name: student_id에 student_name이 각각 대응됨 
course_id → course_name: course_id에 course_name이 각각 대응됨
```

```text
복합키 전체가 아니라 일부에만 의존하는 열을 분리해야 하는 이유: 학생 이름과 과목 이름이 여러 행에 반복 될 경우
학생이나 과목 정보를 성적 기록과 별도로 등록하거나 삭제하기 어려워지는 문제도 생기므로 별도의 테이블로 관리해야 함
```

## 3-3. 제3정규형(3NF)

```text
member_id → zip_code
zip_code → city
member_id → zip_code → city 구조로 회원 ID가 우편번호를 결정하고, 우편번호가 도시를 결정함
```

```text
일반 열이 다른 일반 열을 결정하는 구조를 검토해야 하는 이유: 
city가 member_id가 아니라 zip_code에 따라 결정되므로 회원 정보에 도시를 함께 저장하면 값이 반복됨
우편번호에 해당하는 도시가 바뀌거나 잘못 입력되면 여러 회원 행을 수정해야 함
우편번호와 도시 정보를 별도 테이블로 관리하면 이런 문제를 줄일 수 있음
```

### 정규화는 값이 반복되기만 하면 무조건 분리하는 것인가요?

```text
값이 반복되는지만 보지 않고, 어떤 열이 어떤 키에 의존하는지와 이상 현상이 생기는지를 함께 살펴야 함
```

# 4. 각 열의 '사실의 주인' 찾기

| 열 | 어떤 사실을 설명하는가 | 주인 테이블 | 이유 |
| --- | --- | --- | --- |
| `member_name` | 회원의 이름 | `members_nf` | 회원을 설명하는 정보임 |
| `member_email` | 회원의 이메일 | `members_nf` | 회원의 현재 연락 정보를 설명함 |
| `book_title` | 도서의 제목 | `books_nf` | 도서를 설명하는 정보임 |
| `author` | 도서의 저자 | `books_nf` | 이 예시에서는 도서 정보에 저자를 함께 저장함 |
| `borrowed_at` | 대여가 시작된 시점 | `loans_nf` | 대여 사건이 발생한 시점을 설명함 |
| `due_at` | 해당 대여 건의 반납 예정일 | `loans_nf` | 대여 건마다 정해지는 정보임 |
| `returned_at` | 해당 대여 건의 실제 반납 시점 | `loans_nf` | 대여 건의 진행·종료 상태를 설명함 |
| `member_id` | 회원의 식별자 | `members_nf` | 회원 테이블의 기본키이며, 대여 테이블에서는 회원을 연결하는 외래키로 사용함 |
| `book_id` | 도서의 식별자 | `books_nf` | 도서 테이블의 기본키이며, 대여 테이블에서는 도서를 연결하는 외래키로 사용함 |

정규화 후 한 행의 의미:

```text
members_nf 한 행 = 회원 한 명의 정보
books_nf 한 행 = 도서 한 권의 정보 
loans_nf 한 행 = 회원 한 명이 도서 한 권을 대여한 기록 한 건 (복합키로 연결)
```

### 현재 사실과 사건 당시 이력을 구분하는 기준

```text
지금도 유효한 회원 이름·이메일, 도서 제목·저자 정보는 회원·도서 테이블에 저장함
대여 당시 발생한 시점과 해당 대여 건의 예정일·반납일은 대여 테이블에 저장함
과거 시점의 값을 보존해야 한다면 당시 값을 대여 기록에 별도로 남겨야 함
```

# 6. Chapter 06에서 확정한 C-01~C-08 정책 해석

| ID | 확정 규칙 | 구현 방법 | 왜 필요한가 | Chapter 05에서는 왜 미확정이었나 |
| --- | --- | --- | --- | --- |
| C-01 | 이메일 문자열 중복 금지 | `UNIQUE` | 한 이메일이 여러 회원에게 등록되는 것을 막음 | 이메일을 고유 식별 정보로 사용할지 업무 규칙 확인이 필요했음 |
| C-02 | ISBN 필수·중복 금지 | `NOT NULL + UNIQUE` | ISBN 없는 도서와 같은 ISBN의 중복 등록을 막음 | ISBN을 모든 도서에 필수로 받을지 정책 결정이 필요했음 |
| C-03 | 이름·제목 공백 금지 | `CHECK` | 공백만 있는 회원 이름이나 도서 제목을 막음 | 어떤 입력을 유효한 값으로 볼지 기준이 필요했음 |
| C-04 | `due_at >= borrowed_at` | `CHECK` | 반납 예정일이 대여일보다 앞서는 오류를 막음 | 날짜의 유효한 순서를 업무 규칙으로 확정해야 했음 |
| C-05 | `returned_at`은 NULL 또는 대여일 이상 | `CHECK` | 대여일보다 앞선 반납일을 막음 | NULL의 의미와 날짜 기준을 정해야 했음 |
| C-06 | 존재하는 회원·도서만 참조 | `FOREIGN KEY` | 등록되지 않은 회원이나 도서의 대여를 막음 | 테이블 간 관계와 참조 대상을 확정해야 했음 |
| C-07 | 대여 이력이 있는 부모 삭제 금지 | `ON DELETE RESTRICT` | 대여 기록이 가리키는 회원·도서가 삭제되는 것을 막음 | 이력 보존과 삭제 허용 범위를 정해야 했음 |
| C-08 | 도서당 미반납 대여 최대 한 건 | `returned_at IS NULL` 조건의 부분 고유 인덱스 | 같은 도서가 동시에 여러 번 대여 처리되는 것을 막음 | 동시 대여를 허용할지 운영 규칙 확인이 필요했음 |

### 확정되지 않은 정책을 제약조건으로 먼저 만들면 위험한 이유


# 9. 정규화와 무결성 제약조건 역할 비교

| 질문 | 나의 설명 |
| --- | --- |
| 정규화가 해결하는 문제 | 서로 다른 사실을 한 테이블에 섞어 저장하면서 생기는 위험한 중복과 삽입·수정·삭제 이상을 줄임 |
| `NOT NULL`이 해결하는 문제 | 반드시 입력되어야 하는 값이 비어 있는 상태로 저장되는 것을 막음 |
| `UNIQUE`가 해결하는 문제 | 이메일이나 종목 식별자처럼 중복되면 안 되는 값의 중복 저장을 막음 |
| `CHECK`가 해결하는 문제 | 가격이 0보다 커야 하는 등, 정해 둔 조건에 맞지 않는 값의 저장을 막음 |
| `FOREIGN KEY`가 해결하는 문제 | 분석 기록이 실제로 존재하는 사용자나 종목을 참조하도록 보장함 |
| 부분 고유 인덱스가 해결하는 문제 | 특정 조건을 만족하는 행에만 고유성을 적용하게 함 |

### 정규화만 잘하면 잘못된 데이터가 모두 차단되나요?

```text
정규화는 데이터 구조와 중복 문제를 다루는 범위로, 필수값 누락이나 입력 오류는 제약조건으로 막아야 함
```

### 제약조건만 많이 넣으면 나쁜 구조가 좋은 구조가 되나요?

```text
제약조건은 정해진 규칙을 지키게 하지만, 중복된 사실이 여러 곳에 저장되는 구조 자체를 해결하지는 못함
```

# 11. AI를 정규화·무결성 리뷰어로 활용

## 11-1. 내가 먼저 작성한 구조와 규칙

```text
내 서비스: 픽로그, 주식 분석 기록과 투자 복기 서비스
검토할 테이블: 사용자, 종목, 투자 분석 기록, 복기 기록
한 행의 의미: 한 사용자가 특정 종목에 대해 특정 시점에 남긴 분석 기록 한 건
중복으로 의심되는 열: 분석 기록마다 반복 저장되는 종목명·시장 정보
확정 업무 규칙: 분석 기록은 실제 사용자와 종목에 연결되어야 함
미확정 정책: 판단 종류, 가격 입력 기준, 투자 근거를 별도 관리할지 여부
```

## 11-2. AI에게 전달한 핵심 프롬프트

```text
픽로그는 사용자가 종목 분석과 투자 판단을 기록하고 나중에 복기하는 서비스야.
각 테이블의 한 행이 무엇을 의미하는지와 열이 어떤 사실에 의존하는지 검토해줘.
위험한 중복, 부분·이행 종속 가능성, 필요한 외래키와 제약조건 후보를 제안해줘.
다만 요구사항에 없는 규칙은 확정하지 말고 확인 질문으로 남겨줘.
특히 같은 종목에 대한 여러 시점의 기록을 막는 UNIQUE 제약조건은 임의로 제안하지 말아줘.
```

## 11-3. AI 제안 검토

| AI 제안 | 수용 / 수정 / 보류 / 거절 | 요구사항 근거 | 실제 검증 방법 | 나의 판단 |
| --- | --- | --- | --- | --- |
| 분석 기록에서 종목 정보를 `stock_id`로 참조 | 수용 | 종목별 기록과 복기 필요 | 등록된 종목 ID로 기록을 조회 | 현재 종목 정보의 중복을 줄이는 제안임 |
